> [!abstract] Определение
> **Текст программы** (*source code*, исходный текст) — запись программы на языке программирования в виде последовательности символов [[Алфавит языка программирования|алфавита]], хранящаяся в одном или нескольких исходных файлах (*source files*) и служащая входом транслятора. Это представление программы, предназначенное для чтения человеком; результаты трансляции и компоновки — объектные и исполняемые файлы — текстом программы уже не являются.

## Примечания и тонкости

- Три уровня, которые нельзя смешивать: **исходный файл** — то, что лежит на диске; **единица трансляции** (*translation unit*) — исходный файл вместе со всем включённым через `#include` содержимым, **за вычетом строк, исключённых директивами условной компиляции** ([lex.separate]); **программа** — набор единиц трансляции, связанных компоновщиком. Оговорка про условную компиляцию не формальность: именно из неё следует, что содержимое `#if 0 … #endif` и повторно включённый через include guard [[Заголовочный файл|заголовочный файл]] в единицу трансляции не входят. Практическая цепочка: исходный текст (`.cpp`, `.h`) → объектный код (`.o`, `.obj`, по одному на единицу трансляции) → исполняемый файл (см. [[Раздельная компиляция]]).
- Стандарт описывает обработку текста девятью **фазами трансляции** ([lex.phases]): 1 — байты файла отображаются в базовый набор символов; 2 — физические строки склеиваются по `\` в конце строки; 3 — текст разбивается на препроцессорные лексемы, и каждый [[Комментарии|комментарий]] заменяется одним пробелом; 4 — работает [[Препроцессор|препроцессор]]: выполняются директивы, раскрываются [[Макрос|макросы]], вставляется содержимое заголовочных файлов; 5 — символьные и [[C-строки и строковые литералы|строковые литералы]] переводятся в набор символов выполнения; 6 — соседние строковые литералы склеиваются (`"ab" "cd"` → `"abcd"`); 7 — препроцессорные лексемы становятся лексемами языка, выполняется синтаксический и семантический анализ, то есть «компиляция» в узком смысле; 8 — инстанцируются шаблоны; 9 — всё компонуется в образ программы. Большинство «загадочных» вопросов о тексте программы снимается указанием номера фазы.
- Каждый включённый через `#include` файл сам рекурсивно проходит фазы 1–4. Отсюда ответ на классический вопрос: незакрытый `/*` «переползти» через `#include` не может.
- Формат текста свободный: пробелы, табуляции и переводы строк значимы только как разделители лексем, их количество не важно, и программу можно записать хоть в одну строку. Пробел важен лишь там, где без него две лексемы слились бы в одну: `int x` против `intx`, `a - -b` против `a--b`. Отступы — исключительно для людей, в отличие от Python.
- Исключений из свободного формата ровно три: перевод строки завершает `//`-комментарий; перевод строки завершает директиву препроцессора; внутри «сырого» строкового литерала `R"(…)"` значим каждый символ, включая перевод строки.
- Разбор на лексемы жаден (*maximal munch*): на каждом шаге берётся самая длинная возможная лексема. Поэтому `a+++b` — это `a ++ + b`, а не `a + ++ b`. До C++11 по схожей причине `vector<vector<int>>` не компилировалось, но исключение, сделанное в C++11, относится не к правилу жадности, а к разбору списка аргументов шаблона ([temp.names]: первый невложенный `>` считается закрывающим) — сам лексер не менялся.
- Разорвать строковый литерал переводом строки непосредственно нельзя. Есть ровно три приёма: `\` в конце строки (склейка на фазе 2), два соседних литерала (склейка на фазе 6) и сырой литерал `R"(…)"`, внутри которого перевод строки становится частью значения.
- Кодировка исходного файла определяется реализацией (GCC и Clang по умолчанию читают UTF-8, кодировка задаётся ключом `-finput-charset`); в C++23 поддержка UTF-8 стала обязательной. Последняя строка файла без завершающего перевода строки с C++11 обрабатывается так, будто перевод строки есть; формально это исправление дефекта (CWG 787), применённое и к более ранним версиям, хотя опубликованный текст C++03 давал здесь неопределённое поведение.
- Соответствие между текстом программы и машинным кодом в исполняемом файле само по себе не хранится — его обеспечивает отладочная информация, которую использует [[Отладчик|отладчик]]; без неё связь строки кода и машинной инструкции теряется.
- **На практике:** UTF-8 без BOM, перевод строки LF, единый стиль оформления через автоформатер (clang-format) и соглашения команды; [[Объявление|объявления]] выносят в заголовочные файлы, [[Определение|определения]] — в файлы реализации.

## Пример

```cpp
#include <iostream>

int main()
{ int a = 1, b = 2;
        int c = a+++b;   // жадный разбор: это (a++) + b
    std::cout << "сво\
бодный формат"           // фаза 2: физические строки склеены по '\'
              << ' ' << c << ' ' << a
              << ' ' << R"(в сыром литерале \n — два символа)" << '\n';
    // выведет: свободный формат 3 2 в сыром литерале \n — два символа
}
```

Отступы здесь намеренно бессмысленны: на смысл программы они не влияют. Обычный литерал разорван только потому, что фаза 2 склеивает строки по обратной косой, — в тексте он остаётся одной лексемой; в сыром литерале, наоборот, `\n` остаётся двумя обычными символами.

## Ловушки на экзамене

- **«Зависит ли смысл программы на C++ от отступов и переводов строк?»** — нет: форматирование значимо лишь как разделение лексем. Исключения — `//`-комментарий, директива препроцессора и сырой строковый литерал.
- **«Сколько единиц трансляции в проекте из `main.cpp`, `math.cpp` и `math.h`?»** — две. Заголовочный файл единицей трансляции не является: его текст вставляется на фазе 4 в каждый `.cpp`, который его подключает, и становится частью соответствующей единицы трансляции.
- **«Чему равно `c` после `int a = 1, b = 2; int c = a+++b;`?»** — `c == 3`, `a == 2`: жадный разбор выделяет `++` первым, получается `(a++) + b`. Разбор определяется лексическим уровнем, а не «смыслом» записи.
- **«Что делает `\` в конце строки?»** — склеивает её со следующей на фазе 2, ещё до разбиения на лексемы. Это используется в многострочных макросах, но срабатывает везде — в том числе в конце `//`-комментария, делая комментарием и следующую строку.
- **«Исходный текст и программа — одно и то же?»** — нет: текст — вход компилятора, программа — результат компоновки одной или нескольких единиц трансляции. Текст с синтаксической ошибкой остаётся текстом, но программы из него не получится.

## Связанные термины

- [[Алфавит языка программирования]] — символы, из которых составлен текст программы.
- [[Комментарии]] — части текста, которые заменяются пробелом на фазе 3 и на смысл программы не влияют.
- [[Препроцессор]] — обрабатывает текст на фазе 4, до синтаксического анализа.
- [[Раздельная компиляция]] — как из нескольких исходных файлов получаются единицы трансляции и программа.
- [[Заголовочный файл]] — исходный файл, предназначенный для включения в другие, а не для отдельной компиляции.
- [[Отладчик]] — инструмент, сопоставляющий выполняемый код строкам текста программы.
- [[Интегрированная среда разработки]] — инструмент для написания и редактирования текста программы.

## Протокол спора

> [!quote]- Как рождалось определение
> **Версия A (Формалист):** «Текст программы (*source code*) — запись программы на языке программирования в виде последовательности символов, хранящаяся в одном или нескольких исходных файлах и служащая входом транслятора. Это представление программы, предназначенное для чтения человеком; результат сборки — исполняемый файл — текстом программы не является.»
>
> **Версия Б (Педагог-практик):** «Текст программы (*source code*, исходный текст) — записанная человеком последовательность символов алфавита языка программирования, которую транслятор (компилятор) переводит в исполняемую программу. В C++ текст программы хранится в исходных файлах (*source files*); исходный файл вместе со всем, что подключено к нему директивами `#include`, образует единицу трансляции (*translation unit*) — порцию текста, которую компилятор обрабатывает за один запуск.»
>
> **Спорные пункты:**
> 1. Определение единицы трансляции. A: пропущена существенная часть — «за вычетом строк, исключённых директивами условной компиляции» ([lex.separate]); без неё выходит, что содержимое `#if 0 … #endif` входит в единицу трансляции. Б: дал определение без этой оговорки. → **Решение:** прав A, оговорка восстановлена. Кроме того, единица трансляции названа не «порцией текста, которую компилятор обрабатывает за один запуск»: это результат фаз 1–4, а «один запуск» — свойство реализации (`g++` за один запуск может обработать несколько единиц трансляции). Сама единица трансляции убрана из определения в примечания — она принадлежит термину «Раздельная компиляция».
> 2. Третье исключение из свободного формата. A: это сырой литерал `R"(…)"`, внутри которого значим каждый символ. Б: «внутри строкового литерала пробелы — часть значения». → **Решение:** прав A. Формулировка Б верна сама по себе, но не отвечает на вопрос, ради которого исключение называют: перевод строки внутрь обычного литерала вставить нельзя вообще. В итог идут все три приёма разрыва литерала (фаза 2, фаза 6, сырой литерал).
> 3. Исключение для `>>` в шаблонах. A: изменён не лексер, а разбор списка аргументов шаблона ([temp.names]). Б: «в C++11 для шаблонов сделано исключение» в пункте про жадный разбор. → **Решение:** прав A, формулировка уточнена: правило maximal munch не менялось.
> 4. Подача фаз трансляции. A: нужен нумерованный перечень девяти фаз с точным распределением событий, включая рекурсивное прохождение фаз 1–4 включаемыми файлами и перевод в набор символов выполнения на фазе 5. Б: фазы 5 и 6 склеены в одну строку, про рекурсивность не сказано. → **Решение:** взят перечень A: он переиспользуется в статьях «Комментарии» и «Препроцессор», и именно из рекурсивности фаз 1–4 следует, что незакрытый `/*` не проходит через `#include`.
> 5. «Последняя строка файла без перевода строки»: Б называет это изменением C++11 относительно C++03, где было UB. → **Решение:** пункт сохранён (у A его нет и он полезен), но с уточнением: формально это исправление дефекта CWG 787, применённое ретроактивно, а не нововведение C++11.
> 6. Пример. A: пример Б делает слишком много дел сразу (макрос + жадный разбор + свободный формат + склейка литералов + `>>`) и тянет за собой тему препроцессора, к термину не относящуюся. → **Решение:** согласен. Взят более короткий пример A, в который добавлен сырой литерал — третье исключение из свободного формата; макрос `SQUARE` убран. Пример проверен: выводит `свободный формат 3 2 в сыром литерале \n — два символа` без предупреждений.
>
> **Итог:** определение — от A, с добавленной из версии Б ссылкой на алфавит и упоминанием исходных файлов. От Б взяты: цепочка «исходный текст → объектный код → исполняемый файл», формулировка про пробел (`int x`/`intx`, `a - -b`/`a--b`), пункт о последней строке без перевода строки, ключ `-finput-charset` и ловушка «исходный текст и программа — одно и то же». От A взяты: нумерованный перечень девяти фаз, триада «файл / единица трансляции / программа», рекурсивность фаз 1–4, три точных исключения из свободного формата, три приёма разрыва литерала и связь с отладочной информацией. Арбитр сам восстановил в определении единицы трансляции оговорку про условную компиляцию, уточнил природу исключения для `>>` и статус правила о последней строке файла.
