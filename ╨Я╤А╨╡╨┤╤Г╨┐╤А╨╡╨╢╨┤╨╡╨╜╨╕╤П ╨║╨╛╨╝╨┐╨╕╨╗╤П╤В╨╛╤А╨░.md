# Предупреждения компилятора

> [!abstract] Определение
> **Предупреждения компилятора** (*compiler warnings*) — диагностические сообщения реализации, которые, в отличие от сообщений об ошибках, не прекращают трансляцию: компилятор указывает на подозрительную или формально некорректную конструкцию [[Текст программы|текста программы]] — вероятную ошибку программиста, возможное неопределённое поведение или непереносимость, — но всё равно порождает объектный код, оставляя решение за программистом.

## Примечания и тонкости

- **Слова «предупреждение» в стандарте нет.** Стандарт оперирует понятием «диагностическое сообщение» (*diagnostic message*) и требует: если программа нарушает диагностируемое правило, то есть является некорректно сформированной (*ill-formed*), реализация обязана выдать хотя бы одно диагностическое сообщение. Делить сообщения на ошибки и предупреждения — решение реализации, а не стандарта; границу меняют и ключи (`-Werror`, `-pedantic-errors`).
- **Отсюда важное следствие:** часть предупреждений GCC и Clang — это обязательная диагностика формально некорректной программы, которую компилятор из снисходительности всё же собирает, приняв конструкцию как расширение. Классический пример — массив переменной длины `int a[n];`, на который g++ сообщает лишь при `-pedantic` (`-Wvla`). Поэтому предупреждение нельзя считать заведомо безвредным замечанием о стиле.
- **Три уровня строгости, которые нужно различать.** *Ill-formed* — диагностика обязательна. *Ill-formed, no diagnostic required* (IFNDR) — программа некорректна, но диагностика не требуется; классический пример — нарушение правила одного [[Определение|определения]], которое проявляется только при [[Раздельная компиляция|раздельной компиляции]]. Неопределённое поведение (UB) — свойство **выполнения**, а не текста программы: диагностика не требуется и в общем случае невозможна, предупреждения о UB появляются лишь постольку, поскольку оптимизатор его заметил.
- **Главные ключи GCC и Clang:**
    - `-Wall` — основной набор; вопреки названию, **не все** предупреждения;
    - `-Wextra` — дополнительный набор (неиспользуемые параметры, сравнение знакового с беззнаковым, `-Wtype-limits` и др.);
    - `-pedantic` (`-Wpedantic`) — диагностика отступлений от стандарта ISO C++, которые компилятор иначе молча принял бы как расширение; `-pedantic-errors` превращает их в ошибки;
    - `-Werror` — считать предупреждения ошибками, сборка прерывается;
    - полезные, но не входящие в `-Wall -Wextra`: `-Wconversion` (сужающие [[Неявные преобразования типов|неявные преобразования]]), `-Wshadow` (затенение имён), `-Wold-style-cast`;
    - `-Wno-имя` отключает конкретное предупреждение; имя печатается в квадратных скобках в конце сообщения, например `[-Wsign-compare]`.
    
    В MSVC аналоги — `/W4` (высокий уровень) и `/WX` (предупреждения как ошибки).
- **Предупреждения, которые чаще всего получает первокурсник:** `-Wparentheses` (`if (x = 5)` — [[Оператор присваивания|присваивание]] вместо сравнения); `-Wsign-compare` (`i < v.size()` — `int` против `size_type`); `-Wunused-variable` и `-Wunused-parameter`; `-Wreturn-type` (функция, возвращающая значение, может завершиться без `return`, — а это UB); `-Wuninitialized` и `-Wmaybe-uninitialized`; `-Wimplicit-fallthrough` (пропущен `break` в `switch`, см. [[Инструкции выбора]]); `-Wtype-limits` (условие, всегда истинное по свойствам типа, — частая причина [[Бесконечный цикл|бесконечного цикла]]).
- **Часть предупреждений в g++ включена по умолчанию** (например, `-Wreturn-type`), но большинство полезных — только с `-Wall -Wextra`.
- **Набор и текст предупреждений зависят от реализации, её версии и уровня оптимизации.** Сообщения, требующие анализа потока данных (`-Wmaybe-uninitialized`), при `-O0` могут не выдаваться вовсе, потому что опираются на результаты оптимизационных проходов. Более того, часть предупреждений не появляется при одной лишь проверке синтаксиса: на функцию без `return` g++ 13.3 с `-fsyntax-only` молчит, а при полной компиляции печатает `control reaches end of non-void function [-Wreturn-type]`. Отсюда правило: **отсутствие предупреждений не доказывает корректность программы.**
- **Стандартные атрибуты влияют на диагностику,** но не гарантируют её: `[[nodiscard]]` побуждает реализацию предупредить об отброшенном результате, `[[maybe_unused]]` — подавить сообщение о неиспользуемой сущности, `[[fallthrough]]` — о «провале» между метками `switch`. Стандарт формулирует это как побуждение (*encouraged*), а не требование; к тому же явное приведение вызова к `void` законно подавляет сообщение о `[[nodiscard]]`.
- **Подавлять предупреждение нужно осознанно и точечно:** исправить код (`static_cast<std::size_t>(i)`, двойные скобки `if ((x = f()))` для намеренного присваивания), пометить сущность атрибутом `[[maybe_unused]]`, в крайнем случае — локальная директива `#pragma` с пояснением. Отключать целую категорию предупреждений для всего проекта из-за одного ложного срабатывания неправильно.
- **На практике:** учебные и промышленные проекты собирают с `-Wall -Wextra -Werror` (или `/W4 /WX`) — код с предупреждениями просто не попадает в репозиторий, и целый класс ошибок устраняется до первого запуска, а не [[Отладчик|отладчиком]]. Уровень предупреждений задаётся в настройках проекта [[Интегрированная среда разработки|среды разработки]] или в файле системы сборки.

## Пример

```cpp
#include <iostream>
#include <vector>

[[nodiscard]] int answer() { return 42; }

int main() {
    std::vector<int> v{3, 1, 2};
    int unused = 42;                      // -Wunused-variable
    answer();                             // -Wunused-result: результат отброшен
    for (int i = 0; i < v.size(); ++i)    // -Wsign-compare: int против size_type
        std::cout << v[i] << ' ';
    std::cout << '\n';
    int x = 0;
    if (x = 5)                            // -Wparentheses: '=' вместо '=='
        std::cout << "x is 5?!\n";
}
```

Пример намеренно составлен так, чтобы выдать предупреждения; программа при этом успешно собирается и запускается:

```text
$ g++ -std=c++20 -Wall -Wextra -pedantic warnings.cpp -o warnings
warnings.cpp:9:11: warning: ignoring return value of 'int answer()', declared with attribute 'nodiscard' [-Wunused-result]
warnings.cpp:4:19: note: declared here
warnings.cpp:10:23: warning: comparison of integer expressions of different signedness: 'int' and 'std::vector<int>::size_type' {aka 'long unsigned int'} [-Wsign-compare]
warnings.cpp:14:11: warning: suggest parentheses around assignment used as truth value [-Wparentheses]
warnings.cpp:8:9: warning: unused variable 'unused' [-Wunused-variable]
$ ./warnings
3 1 2
x is 5?!
```

Каждое из четырёх сообщений указывает на реальный дефект, а ветка `if` выполнилась, хотя `x` был равен `0`: условие `x = 5` присваивает, а не сравнивает. Без `-Wall -Wextra` g++ не сообщил бы ни об одной из этих проблем, кроме `-Wunused-result`; с `-Werror` сборка остановилась бы.

## Ловушки на экзамене

- **Чем ошибка отличается от предупреждения по стандарту?** — Стандарт такого деления не вводит: он требует лишь «диагностическое сообщение» для некорректно сформированной программы. Практически: при ошибке исполняемый файл не создаётся, при предупреждении создаётся, а границу задают реализация и ключи (`-Werror`, `-pedantic-errors`).
- **Программа скомпилировалась, пусть и с предупреждениями, — значит, она правильная?** — Нет. Предупреждение может быть обязательной диагностикой формально некорректной программы, а «работает» для программы с неопределённым поведением ничего не доказывает: поведение способно измениться от смены уровня оптимизации, версии или компилятора.
- **Означает ли отсутствие предупреждений отсутствие ошибок?** — Нет. Целые классы дефектов — выход за границы [[Встроенный массив|массива]] по вычисляемому индексу, висячий указатель, гонка данных — относятся к UB, диагностика которого не требуется и в общем случае невозможна; логические ошибки (например, целочисленное деление вместо дробного) компилятор тоже не видит.
- **`-Wall` включает все предупреждения?** — Нет, только основной набор. `-Wextra`, `-Wconversion`, `-Wshadow` и многие другие включаются отдельно; название сохранилось по историческим причинам.
- **Что делает `-pedantic`?** — Требует диагностику для конструкций, запрещённых стандартом, но принимаемых компилятором как расширение. Без него такой код проходит молча и перестаёт быть переносимым.
- **Функция `int sign(int x)` без `return` для `x == 0` проходит все тесты. Можно ли игнорировать `control reaches end of non-void function`?** — Нет. При `x == 0` выполнение дойдёт до конца функции без `return`, а это UB: «правильный» результат на тестах — случайность, которая исчезнет при другом уровне оптимизации или компиляторе.
- **Почему одна и та же программа даёт предупреждение при `-O2` и не даёт при `-O0`?** — Предупреждения, основанные на анализе потока данных, опираются на результаты оптимизационных проходов; при выключенной оптимизации этот анализ не выполняется. По той же причине `-fsyntax-only` не выдаёт `-Wreturn-type`. Это не ошибка компилятора, а следствие его устройства.
- **У студента предупреждений нет, а у преподавателя на том же коде есть. Почему?** — Разные компиляторы, версии, ключи или уровень оптимизации: без `-Wall -Wextra` g++ молчит почти обо всём.
- **Является ли `[[nodiscard]]` гарантией предупреждения?** — Нет: стандарт лишь побуждает реализацию выдать диагностику. Кроме того, явное приведение вызова к `void` подавляет сообщение законным образом.

## Связанные термины

- [[Отладчик]] — следующая линия поиска ошибок там, где компилятор промолчал.
- [[Интегрированная среда разработки]] — показывает предупреждения как навигируемый список проблем проекта; там же задаются ключи.
- [[static_assert]] — способ получить собственную диагностику на этапе компиляции, причём в виде ошибки, а не предупреждения.
- [[Неявные преобразования типов]] — источник целой группы предупреждений (`-Wconversion`, `-Wsign-compare`).
- [[Инициализация]] — предупреждения о чтении неинициализированных переменных.
- [[Раздельная компиляция]] — нарушение правила одного определения как пример IFNDR, о котором предупреждения не будет.
- [[Оператор присваивания]] — `=` вместо `==` в условии: классический случай, выявляемый предупреждением.
- [[Инструкции выбора]] — предупреждение о пропущенном `break` между метками `switch`.

## Протокол спора

> [!quote]- Как рождалось определение
> **Версия A (Формалист):** «Предупреждения компилятора (*compiler warnings*) — диагностические сообщения реализации, которые, в отличие от ошибок, не прекращают трансляцию: компилятор сообщает о подозрительной или формально некорректной конструкции, но всё равно порождает объектный код, оставляя решение за программистом.»
>
> **Версия Б (Педагог-практик):** «Предупреждения компилятора (*compiler warnings*) — диагностические сообщения компилятора, которые, в отличие от сообщений об ошибках, не останавливают сборку, но указывают на подозрительный фрагмент текста программы: вероятную ошибку программиста, возможное неопределённое поведение или непереносимую конструкцию.»
>
> **Спорные пункты:**
> 1. «Сообщения реализации» или «сообщения компилятора». → **Решение:** взято «реализации» (A): стандарт говорит именно о реализации, а сообщения выдаёт не только собственно компилятор (часть диагностики приходит от компоновщика). Слово «компилятор» при этом остаётся в самом заголовке термина как общепринятое.
> 2. «Не прекращают трансляцию» (A) против «не останавливают сборку» (Б). → **Решение:** взято A: «трансляция» — термин стандарта, и он точнее описывает, что именно не прерывается.
> 3. Что именно сообщает предупреждение. A: «о подозрительной или формально некорректной конструкции». Б: то же плюс расшифровка — «вероятную ошибку программиста, возможное UB или непереносимую конструкцию». → **Решение:** расшифровка Б принята и вставлена в определение через тире: она отвечает на вопрос «о чём бывают предупреждения» и не является ни примером, ни оговоркой. Важное «формально некорректной» от A сохранено — именно оно отличает предупреждение от замечания о стиле.
> 4. «Порождает объектный код, оставляя решение за программистом» — только у A. → **Решение:** сохранено: это и есть рабочее отличие от ошибки, по которому студент узнаёт предупреждение на практике.
> 5. **Уровни строгости.** A различает *ill-formed*, IFNDR и UB и объясняет, что UB — свойство выполнения, а не текста программы, поэтому диагностика невозможна. У Б этого нет вовсе. → **Решение:** взято A целиком. Это лучший фрагмент обеих версий: без различения IFNDR и UB ответ на вопрос «почему компилятор не поймал ошибку» остаётся на уровне «не умеет».
> 6. Почему некорректный код проходит с одним предупреждением. A называет `-pedantic` как механизм вообще. Б даёт конкретный пример — массив переменной длины `int a[n];` (`-Wvla`) и `-pedantic-errors`. → **Решение:** объединено: механизм A плюс конкретный пример Б, который студент легко воспроизведёт.
> 7. Перечни ключей и типовых предупреждений. У Б они существенно полнее и ближе к опыту первокурсника (`-Wno-имя`, имя ключа в квадратных скобках, перечень «что чаще всего получает первокурсник», `/W4 /WX`). У A есть `-Wold-style-cast`, отсутствующий у Б. → **Решение:** взяты перечни Б, дополненные `-Wold-style-cast` от A и `-Wtype-limits` (арбитр: этот ключ упоминается обеими статьями о циклах, и его стоит назвать здесь).
> 8. Зависимость диагностики от этапа компиляции. Б утверждает, что `-Wreturn-type` не выдаётся при `-fsyntax-only`, а `-Wmaybe-uninitialized` — только при `-O2`. → **Решение:** проверено компилятором и подтверждено: на `int sign(int x) { if (x > 0) return 1; if (x < 0) return -1; }` g++ 13.3 с `-fsyntax-only` молчит, а при полной компиляции печатает `control reaches end of non-void function [-Wreturn-type]`. Факт принят с точной формулировкой и использован в ловушке; объяснение «почему» взято от A (анализ потока данных опирается на оптимизационные проходы).
> 9. Стандартные атрибуты. Только у A: `[[nodiscard]]`, `[[maybe_unused]]`, `[[fallthrough]]` — и главное, что стандарт лишь *побуждает* (*encouraged*) выдать диагностику, а приведение к `void` её законно подавляет. → **Решение:** принято: это неочевидная тонкость, за которую на экзамене ставят плюс.
> 10. Пример. A: `[[nodiscard]]`-функция, `if (n = argc)` и неиспользуемый параметр. Б: неиспользуемая переменная, `-Wsign-compare` на `i < v.size()`, `if (x = 5)` плюс сеанс оболочки с настоящим выводом компилятора и запуском. → **Решение:** примеры объединены, потому что дополняют друг друга: взята программа Б (в ней есть `-Wsign-compare` — самое частое предупреждение у первокурсника и наглядный запуск, показывающий, что ветка `if` всё равно выполнилась) и добавлена `[[nodiscard]]`-функция от A. Неиспользуемые `argc`/`argv` из примера A убраны: два лишних сообщения про параметры `main` только загромождают вывод. Итоговый вариант собран и запущен; текст предупреждений, номера строк и столбцов в статье — фактический вывод g++ 13.3.
>
> **Итог:** определение — A по рамке («реализации», «трансляцию», «порождает объектный код»), с расшифровкой «о чём бывает предупреждение» от Б. От A взяты: отсутствие слова «предупреждение» в стандарте и понятие диагностического сообщения, три уровня строгости (*ill-formed*, IFNDR, UB) и объяснение, почему UB не диагностируется, роль стандартных атрибутов как побуждения, а не гарантии, зависимость набора предупреждений от версии и уровня оптимизации, ловушки про стандарт, про `[[nodiscard]]` и про `-O2`/`-O0`. От Б взяты: перечни ключей с `-Wno-имя` и именем ключа в скобках, `/W4 /WX`, список типовых предупреждений первокурсника, пример с массивом переменной длины и `-pedantic-errors`, включённые по умолчанию предупреждения g++, зависимость от `-fsyntax-only`, программа-пример с реальным выводом компилятора, ловушки про `-Wall`, про функцию `sign` без `return` и про расхождение у студента и преподавателя. Фактических ошибок у авторов в этой статье не обнаружено; два спорных утверждения Б о поведении g++ проверены компилятором и подтверждены.
