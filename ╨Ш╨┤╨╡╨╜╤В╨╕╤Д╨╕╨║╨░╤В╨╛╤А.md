# Идентификатор

> [!abstract] Определение
> **Идентификатор** (*identifier*) — лексема, служащая именем сущности в программе: последовательность букв, цифр и знаков подчёркивания, не начинающаяся с цифры и не совпадающая с ключевым словом. Какую именно сущность обозначает идентификатор, задаётся его [[Объявление|объявлением]].

## Примечания и тонкости

- Лексический и синтаксический уровни надо разделять: из каких символов может состоять имя — вопрос лексики ([lex.name]) и [[Алфавит языка программирования|алфавита]]; что именно это имя обозначает — [[Переменная|переменную]], [[Функция|функцию]], [[Тип данных|тип]], [[Пространство имён|пространство имён]], метку — вопрос объявления и [[Область видимости|области видимости]]. Один и тот же идентификатор `x` в разных областях видимости обозначает разные сущности.
- Идентификатор и имя — не одно и то же. Идентификатор — понятие лексическое («как записано»); имя — то, что обозначает конкретную сущность, и не всякое имя является идентификатором (`operator+` — имя, но не идентификатор). Идентификатор — и не сущность: переменная существует независимо от того, как её записали.
- Регистр значим, и значим каждый символ: `count`, `Count` и `COUNT` — три разных идентификатора, а `Main` — не `main`.
- Длину идентификатора стандарт не ограничивает, и значимы **все** символы (в отличие от старого C, где значимыми могли быть только первые 31). Annex B лишь рекомендует реализациям поддерживать не менее 1024 значимых символов, и эти рекомендации не нормативны.
- Что считается «буквой»: `a`–`z`, `A`–`Z` и универсальные имена символов из разрешённых диапазонов Annex E, поэтому `int счётчик = 0;` в C++20 законен и принимается GCC 10+ и Clang. Знак `_` формально не буква, а отдельный *identifier-start*. В C++23 (P1949) правило переформулировано через свойства Юникода `XID_Start` / `XID_Continue` и добавлено требование нормализации NFC. `$` в имени — расширение компиляторов, а не стандарт.
- Ключевые слова лексически **являются** идентификаторами: на фазах 3–4 трансляции `if` — обычная препроцессорная лексема-идентификатор, ключевым словом она становится только при превращении препроцессорных лексем в лексемы языка на фазе 7. Отсюда следствие: имя [[Макрос|макроса]] лексически может совпасть с ключевым словом (стандартной библиотеке это запрещено отдельно, [macro.names]). Фраза «идентификатор не совпадает с ключевым словом» — правило не лексическое, а синтаксическое.
- Зарезервированные имена: идентификатор, содержащий `__` где угодно внутри, и идентификатор, начинающийся с `_` и заглавной буквы, зарезервированы реализации в **любом** контексте; идентификатор, начинающийся с `_`, зарезервирован в глобальном пространстве имён. Использование такого имени делает программу **некорректной, но диагностика не требуется** (*ill-formed, no diagnostic required*) — это не UB: один компилятор примет код молча, другой сломается. Проверено: `int __value = 0; int _Tmp = 1;` GCC 13 принимает с `-Wall -Wextra -pedantic` без единого слова. UB возникает в другом случае — при объявлении имени, зарезервированного стандартной библиотекой ([reserved.names]).
- Идентификаторы с особым значением — `override`, `final`, а с C++20 также `import` и `module` — **не** ключевые слова: особое значение у них только в своём месте синтаксиса, поэтому `int final = 0;` корректно. Именно поэтому их не пришлось добавлять в список ключевых слов, ломая старый код.
- Имя макроса — тоже идентификатор, но подстановка выполняется на фазе 4, до всякого анализа имён. Поэтому макрос с коротким общеупотребительным именем (`min`, `max`) ломает обращения к одноимённым функциям, и никакая область видимости от него не спасает.
- **На практике:** имя должно говорить о назначении сущности, а не о её типе: `studentCount` лучше, чем `n1`. Принятое в проекте соглашение (`snake_case`, `camelCase`, `PascalCase` для типов, `UPPER_CASE` только для макросов) важнее личного вкуса, а имена, начинающиеся с подчёркивания, не использовать вообще — слишком велик риск столкнуться с внутренним именем реализации.

## Пример

```cpp
#include <iostream>

int main() {
    int count = 1, Count = 2;   // разные имена: регистр значим
    int x2 = 3;                 // цифра допустима, но не первой
    int _tmp = 4;               // в блоке допустимо: '_' + строчная буква
    int final = 5;              // final — идентификатор с особым значением, не ключевое слово
    // int 2x = 0;       // ошибка: 2x — препроцессорная лексема-число, а не имя
    // int my-var = 0;   // ошибка: '-' не входит в состав идентификатора
    // int class = 0;    // ошибка: class — ключевое слово
    // int __value = 0;  // компилируется молча, но имя зарезервировано реализации
    std::cout << count + Count + x2 + _tmp + final << '\n';   // выведет: 15
}
```

Имя `_tmp` внутри блока формально допустимо (зарезервирован только `_` в глобальном пространстве имён), но писать так не следует. Строка с `__value` закомментирована не потому, что компилятор её отвергнет, а потому, что она делает программу некорректной без всякой диагностики.

## Ловушки на экзамене

- **«Какие из имён допустимы: `2x`, `x2`, `_x`, `my-var`, `my_var`, `int`, `Int`?»** — допустимы `x2`, `my_var`, `Int` и `_x` (но в глобальном пространстве имён `_x` зарезервирован). `2x` начинается с цифры; `my-var` — это три лексемы `my`, `-`, `var`; `int` — ключевое слово, а `Int` — уже нет, потому что регистр значим.
- **«`int 2x = 5;` — ошибка лексическая или синтаксическая?»** — тонкий случай: `2x` — вполне корректная препроцессорная лексема-число (*pp-number*), но на фазе 7 она не превращается ни в одну лексему языка, поэтому программа некорректна. Сообщение компилятора будет «не про имя»: GCC 13 выдаёт `expected unqualified-id before numeric constant`, а в выражении `int x = 2x;` — `unable to find numeric literal operator 'operator""x'`, то есть ищет литеральный суффикс.
- **«`main`, `cout`, `vector` — ключевые слова?»** — нет, это обычные идентификаторы: имя главной [[Функция main|функции программы]] и имена сущностей из пространства имён `std`. В списке ключевых слов C++20 их нет.
- **«Чем различаются `_tmp`, `__tmp` и `_Tmp`?»** — `__tmp` и `_Tmp` зарезервированы реализации везде, поэтому использовать их нельзя никогда; программа с ними некорректна, хотя компилятор вправе промолчать. `_tmp` запрещён только в глобальном пространстве имён; внутри функции или класса допустим, но стилистически нежелателен.
- **«`final` и `override` — ключевые слова?»** — нет, идентификаторы с особым значением. Переменную можно назвать `final`, и это скомпилируется; хорошим стилем, впрочем, не считается.
- **«Идентификатор и переменная — одно и то же?»** — нет: переменная — сущность, введённая объявлением [[Объект|объекта]] или ссылки, а идентификатор — лишь её запись в тексте. Не у каждого объекта есть имя: элемент массива `a[3]` — объект, но не переменная, и собственного идентификатора у него нет.

## Связанные термины

- [[Алфавит языка программирования]] — задаёт, из каких символов идентификатор может состоять.
- [[Объявление]] — конструкция, которая связывает идентификатор с конкретной сущностью.
- [[Переменная]] — самая частая сущность, которой идентификатор служит именем.
- [[Область видимости]] — область текста, в которой идентификатор обозначает данную сущность.
- [[Пространство имён]] — способ развести одинаковые идентификаторы из разных библиотек.
- [[Макрос]] — идентификатор, обрабатываемый до анализа имён, отсюда его конфликты с обычными именами.
- [[Ключевое слово override]] — пример идентификатора с особым значением, а не ключевого слова.

## Протокол спора

> [!quote]- Как рождалось определение
> **Версия A (Формалист):** «Идентификатор (*identifier*) — лексема, служащая именем сущности в программе: последовательность букв, цифр и знаков подчёркивания, не начинающаяся с цифры и не совпадающая с ключевым словом. Сам идентификатор никакого смысла не несёт: какую сущность он обозначает, задаётся его объявлением.»
>
> **Версия Б (Педагог-практик):** «Идентификатор (*identifier*) — лексема, представляющая собой последовательность букв, цифр и знаков подчёркивания, которая начинается не с цифры и не совпадает с ключевым словом. Идентификаторы служат именами сущностей программы: переменных, функций, типов, пространств имён и т. д.»
>
> **Спорные пункты:**
> 1. Статус зарезервированных имён. A: программа некорректна, но диагностика не требуется (*ill-formed, no diagnostic required*). Б: это неопределённое поведение (UB), причём компилятор обычно молчит. → **Решение:** прав A. [lex.name] говорит «shall not be used otherwise; no diagnostic is required», то есть IFNDR, а не UB; UB предусмотрено отдельно для имён, зарезервированных стандартной библиотекой ([reserved.names]). Регламент прямо требует не смешивать эти категории. Практический вывод тоже другой: не «при запуске может случиться что угодно», а «программа некорректна уже сейчас, просто этот компилятор молчит» (проверено на GCC 13).
> 2. «У одной переменной может не быть собственного имени (элемент массива `a[3]`)» — так у Б. → **Решение:** формулировка исправлена. По принятой в справочнике терминологии `a[3]` — объект, но не переменная: никакое объявление его не вводит. В итог идёт «не у каждого объекта есть имя».
> 3. Механизм ошибки `2x`. A: `2x` — препроцессорная лексема-число, и сообщение компилятора говорит про литеральный суффикс, а не про плохое имя. Б: «идентификатор не может начинаться с цифры». → **Решение:** прав A по механизму, но его цитата сообщения GCC оказалась неверной. Проверено: `int 2x = 5;` даёт `expected unqualified-id before numeric constant`, а заявленное A `invalid suffix "x" on integer constant` GCC 13 в режиме C++20 не выдаёт; сообщение про `operator""x` возникает в выражении (`int x = 2x;`). В итог идут оба реальных сообщения.
> 4. Ключевые слова и лексический уровень. A: ключевые слова лексически являются идентификаторами и становятся ключевыми только на фазе 7, отсюда поведение макросов. Б: пункта нет. → **Решение:** взято у A: без него нельзя объяснить ни статус `override`/`final`, ни то, почему имя макроса может совпасть с ключевым словом.
> 5. Противоречие «идентификатор служит именем» против «идентификатор и имя — не одно и то же». A: у Б определение и примечание спорят друг с другом по тону, надо выбрать одну формулировку. → **Решение:** определение оставлено в редакции A (вторая фраза переадресует вопрос «что обозначает» объявлению), а точное разграничение идентификатора и имени — в редакции Б, с упоминанием `operator+`.
> 6. «Ключевых слов в C++ около сотни» — так у Б. → **Решение:** цифра убрана. Таблица ключевых слов C++20 содержит порядка восьми десятков имён плюс 11 альтернативных представлений; неточное число на устном ответе хуже, чем его отсутствие.
> 7. Что лишнее. A: у Б пункт про соглашения об именовании — это стиль, а не теория термина, и он дублируется с «На практике»; пункт «`main`, `std`, `cout` — идентификаторы» дословно повторяет одноимённую ловушку. → **Решение:** согласен. Соглашения свёрнуты в один пункт «На практике»; дублирующий пункт убран, ловушка оставлена.
>
> **Итог:** определение — от A. От Б взяты: цифра 1024 из Annex B и сравнение со старым C (31 значимый символ), разграничение идентификатора и имени, ловушка про `main`/`cout`, ловушка про перечень допустимых имён и подтверждённое компилятором утверждение, что `int счётчик = 0;` законен. От A взяты: разделение лексического и синтаксического уровней, статус ключевых слов на фазах 3–7, корректная категория IFNDR вместо UB, механизм pp-number, поведение макросов на фазе 4. Арбитр исправил у Б «UB» на IFNDR и «переменная `a[3]`» на «объект `a[3]`», а у A — ошибочно приведённый текст диагностики GCC для `int 2x = 5;` (проверено компилятором) и снял его оговорку о том, что кириллица в именах — лишь расширение реализации.
