# Отладчик

> [!abstract] Определение
> **Отладчик** (*debugger*) — служебная программа, управляющая выполнением другой программы: она запускает её под своим контролем или подключается к уже работающей и позволяет приостанавливать её в заданных точках, выполнять по шагам и читать либо изменять её состояние — значения переменных, кадры [[Стек вызовов|стека вызовов]], регистры и содержимое памяти.

## Примечания и тонкости

- **Отладка** (*debugging*) — процесс поиска и устранения ошибок; отладчик — лишь один из её инструментов, наряду с отладочной печатью, [[Логирование|логированием]], тестами и проверками `assert`.
- **Отладочная информация.** Чтобы сопоставить машинный код строкам исходного текста, именам и типам, нужна отладочная информация, порождаемая ключом `-g`: таблицы DWARF в GCC и Clang, файл PDB в MSVC. Сама по себе она не меняет семантику программы и не замедляет её выполнение — лишь увеличивает файл. Без `-g` отладчик работает только на уровне машинных инструкций и адресов.
- **Отладочная информация и оптимизация независимы.** При `-O2 -g` отладчик честно показывает фактически исполняемый код: переменные бывают `<optimized out>`, инструкции переупорядочены, пошаговое выполнение «скачет» по строкам. Для отладки собирают с `-O0 -g` или `-Og -g` (в IDE это конфигурация Debug).
- **Базовые понятия (в скобках — команды GDB):**
    - **точка останова** (*breakpoint*; `break файл:строка`, `break функция`) — место в коде, дойдя до которого программа приостанавливается; **условная** точка останова (`break 42 if i == 99`) срабатывает только при истинном условии — незаменима в цикле на миллион итераций;
    - **пошаговое выполнение**: *step over* — выполнить строку целиком, не заходя в вызываемые [[Функция|функции]] (`next`); *step into* — войти внутрь вызываемой функции (`step`); *step out* — доработать текущую функцию и вернуться в вызывающую (`finish`); `continue` — продолжить до следующей точки останова;
    - **просмотр и изменение значений**: `print выражение`, `info locals`, окно Watch в IDE; значение можно поменять на ходу (`set var x = 5`) и посмотреть, как поведёт себя программа;
    - **точка наблюдения** (*watchpoint*; `watch x`) — остановка в момент изменения значения объекта, в каком бы месте программы оно ни произошло: помогает найти, «кто испортил» данные;
    - **кадр** (*frame*) и **стек вызовов** (`backtrace`, `bt`) — цепочка вызовов, приведшая в текущую точку, и переход между её звеньями; первое, что смотрят при падении программы.
- **Распространённые отладчики:** GDB (проект GNU, Linux), LLDB (проект LLVM, macOS), отладчик Visual Studio, WinDbg. Кнопки Step Over / Step Into / Step Out в [[Интегрированная среда разработки|среде разработки]] — графическая оболочка над ними.
- **Посмертная отладка** (*post-mortem*): после аварийного завершения ОС может сохранить дамп памяти (*core dump*), который открывают в отладчике (`gdb ./app core`) и смотрят стек вызовов на момент падения, не запуская программу заново.
- **Отладчик не обнаруживает неопределённое поведение.** Он показывает, что программа делает фактически, а не то, что она обязана делать по стандарту. Автоматически ловить ошибки работы с памятью и UB помогают другие средства — санитайзеры (`-fsanitize=address,undefined`), Valgrind, статический анализ; это динамический и статический анализ, а не отладка.
- **«Гейзенбаг»** (*heisenbug*): отладчик изменяет условия выполнения — иная раскладка стека, отсутствие оптимизаций, иной тайминг, — поэтому симптом «под отладчиком работает, без него падает» характерен для UB, а ошибки, зависящие от времени (гонки данных), под ним могут исчезать вовсе. Для таких случаев применяют логирование и thread sanitizer.
- **Не смешивать отладчик со средствами самой программы.** `assert`, отключаемый макросом `NDEBUG`, отладочная печать и [[static_assert|static_assert]] — часть кода программы (а `static_assert` вообще работает на этапе компиляции, см. [[Программирование по контракту]]); отладчик же внешен к программе и её кода не требует.
- **На практике:** продуктивная отладка начинается не с пошагового прохода, а с воспроизводимого минимального примера и проверяемой гипотезы; точка останова ставится туда, где уже известно, что инвариант нарушен, а назад двигаются по стеку вызовов. Первое действие при падении программы — запустить её под отладчиком и выполнить `bt`; умение за минуту поставить точку останова и прочитать стек экономит часы отладочной печати.

## Пример

Программа компилируется без единого предупреждения при `-Wall -Wextra -pedantic`, но печатает `4` вместо `4.25`:

```cpp
#include <iostream>

int sum_marks(const int* m, int n) {
    int s = 0;
    for (int i = 0; i < n; ++i)
        s += m[i];
    return s;
}

int main() {
    const int marks[] = {5, 4, 4, 4};
    const int count = 4;
    int sum = sum_marks(marks, count);
    double average = sum / count;       // ожидали 4.25, получили 4
    std::cout << average << '\n';       // выведет: 4
}
```

Сеанс GDB, находящий причину за несколько команд:

```text
$ g++ -std=c++20 -Wall -Wextra -pedantic -g -O0 average.cpp -o average
$ gdb -q ./average

(gdb) run

6	        s += m[i];
(gdb) bt
#0  sum_marks (m=0x7fffffffaeb0, n=4) at average.cpp:6
#1  0x0000555555555221 in main () at average.cpp:13
(gdb) print i
$1 = 0
(gdb) print s
$2 = 0
(gdb) delete 1
(gdb) break 14
Breakpoint 2 at 0x555555555224: file average.cpp, line 14.
(gdb) continue
Breakpoint 2, main () at average.cpp:14
14	    double average = sum / count;       // ожидали 4.25, получили 4
(gdb) print sum
$3 = 17
(gdb) print sum / count
$4 = 4
(gdb) print (double)sum / count

(gdb) next
15	    std::cout << average << '\n';       // выведет: 4
(gdb) info locals
marks = {5, 4, 4, 4}

sum = 17

(gdb) continue
4

```

`bt` показывает стек вызовов: `sum_marks` вызвана из `main` со строки 13. На первом попадании в точку останова `i == 0` и `s == 0` — тело цикла ещё не выполнялось. Решающие две команды — `print sum / count` и `print (double)sum / count`: слагаемые верны, а виновато целочисленное деление, теряющее дробную часть **до** присваивания в `double`. Исправление — `static_cast<double>(sum) / count`.

## Ловушки на экзамене

- **Отладчик — это часть компилятора?** — Нет, отдельная программа. Компилятор лишь добавляет в исполняемый файл отладочную информацию (ключ `-g`), которую отладчик потом читает.
- **Зачем ключ `-g`, если программа компилируется и без него?** — Без отладочной информации отладчик не знает ни номеров строк, ни имён и типов переменных и работает на уровне адресов. На семантику программы `-g` не влияет.
- **Почему при `-O2` отладчик печатает `<optimized out>` и «прыгает» по строкам?** — Оптимизатор размещает переменную в регистре, сливает её с другой или устраняет вовсе, а инструкции разных строк перемешивает. Отображается фактически исполняемая программа, а не исходный текст. Для отладки нужна сборка `-O0 -g` или `-Og -g`.
- **Чем step over отличается от step into?** — На строке с вызовом функции step over (`next`) выполняет вызов целиком и останавливается на следующей строке, а step into (`step`) заходит внутрь вызываемой функции. На строке без вызовов они ведут себя одинаково.
- **Чем точка останова отличается от точки наблюдения?** — Точка останова привязана к месту в коде («остановиться на строке 10»), точка наблюдения — к данным («остановиться, когда изменится `x`», где бы это ни произошло).
- **Найдёт ли отладчик выход за границы массива?** — Сам по себе нет: выход за границы — неопределённое поведение, а не диагностируемая ошибка; отладчик лишь покажет последствия. Обнаруживает такое AddressSanitizer.
- **Отладчик показывает у только что объявленной `int x;` значение `32767`. Откуда оно?** — Неинициализированная локальная переменная содержит то, что осталось в памяти от предыдущих вызовов; чтение её значения в программе — UB. Отладчик просто показывает содержимое памяти, осмысленное значение появится только после [[Инициализация|инициализации]].
- **«Под отладчиком ошибка пропала — значит, её нет»?** — Нет. Это типичный признак неопределённого поведения или гонки потоков: другая раскладка памяти или другой тайминг маскируют ошибку. Искать её нужно санитайзерами, логированием и [[Предупреждения компилятора|предупреждениями компилятора]].

## Связанные термины

- [[Стек вызовов]] — то, что отладчик показывает по команде `backtrace`; основа навигации при падении.
- [[Интегрированная среда разработки]] — графическая оболочка, через которую отладчик обычно и используется.
- [[Предупреждения компилятора]] — первая линия обороны: многое из того, что ищут отладчиком, компилятор сообщает сразу.
- [[Логирование]] — альтернатива отладчику там, где остановка программы искажает картину.
- [[Программирование по контракту]] — `assert` и проверки инвариантов как средства, встроенные в саму программу.
- [[Модель памяти]] — чтобы понимать, что показывают окна памяти и регистров.
- [[Инициализация]] — «мусорные» значения неинициализированных переменных, видимые в отладчике.
- [[Бесконечный цикл]] — пауза в отладчике показывает, где именно зависла программа.

## Протокол спора

> [!quote]- Как рождалось определение
> **Версия A (Формалист):** «Отладчик (*debugger*) — служебная программа, управляющая выполнением другой программы: она позволяет приостанавливать её в заданных точках, выполнять по шагам и читать либо изменять её состояние — значения переменных, кадры стека вызовов, регистры и содержимое памяти.»
>
> **Версия Б (Педагог-практик):** «Отладчик (*debugger*) — программа, которая запускает другую программу (или подключается к уже работающей) под своим контролем и позволяет приостанавливать её в заданных местах, выполнять пошагово, просматривать и изменять значения переменных, стек вызовов и содержимое памяти.»
>
> **Спорные пункты:**
> 1. Видовое отличие: «управляющая выполнением» (A) против «запускает или подключается» (Б). → **Решение:** взят род и видовое отличие A — «служебная программа, управляющая выполнением другой программы» — как более общая формулировка, охватывающая и посмертную отладку по дампу памяти, где никакого «запуска» нет. Но существенное уточнение Б («или подключается к уже работающей») внесено в определение: без него студент не знает, что отладчик можно прицепить к запущенному процессу.
> 2. Перечень того, что видно. A: значения переменных, **кадры** стека, **регистры**, память. Б: значения, стек вызовов, память. → **Решение:** взят перечень A: «кадры» — правильное название, а регистры студент увидит в любой IDE и должен знать, что это тоже часть состояния.
> 3. Различение отладки и отладчика. Только у Б: отладка — процесс, отладчик — один из инструментов наряду с печатью, логированием, тестами, `assert`. → **Решение:** принято первым пунктом примечаний: это ровно та граница понятия, которую путают на экзамене.
> 4. Перечень команд GDB. У Б он подробный и с привязкой к русским названиям действий (step over / step into / step out, `next`/`step`/`finish`, `set var`, `info locals`), у A — без конкретных команд, кроме `step`/`next`/`continue`. → **Решение:** взят перечень Б целиком, в него добавлены от A «кадр» как термин и переход между кадрами. Все приведённые команды проверены в реальном сеансе GDB 15.1.
> 5. Что именно не умеет отладчик. A: «не обнаруживает UB», и это утверждение усилено тем, что отладчик показывает фактическое, а не обязательное поведение. Б: «отладчик не находит ошибки сам», санитайзеры и Valgrind — средства динамического анализа. → **Решение:** соединено: формулировка A как принципиальная (UB не диагностируется) плюс перечень альтернативных средств Б.
> 6. Нужно ли отличать отладчик от `assert` и `static_assert`. Только у A. → **Решение:** принято: `assert` и `static_assert` — часть программы, отладчик внешен к ней; студенты регулярно относят `assert` к «средствам отладчика».
> 7. **Пример — главное расхождение по существу.** A: вычисление факториала, точка останова в цикле; сеанс GDB в режиме `-batch` показывает, что `i == 2`, а `acc` ещё `1`. Б: ошибка целочисленного деления `sum / count` при подсчёте среднего; интерактивный сеанс GDB, в котором видно и `print sum / count` = `4`, и `print (double)sum / count` = `4.25`. → **Решение:** взят пример Б. У A пример демонстрирует механику отладчика, но в программе нет ошибки — непонятно, зачем её вообще отлаживают; у Б отладчик решает реальную задачу и заодно иллюстрирует тезис «компилятор промолчал, а ошибка есть». Арбитр доработал пример: вычисление суммы вынесено в отдельную функцию, чтобы `bt` показывал стек из двух кадров (у Б стек был из одного, и демонстрация `backtrace` теряла смысл). Программа собрана с `-Wall -Wextra -pedantic` — предупреждений действительно нет, — и сеанс GDB **проведён заново**: все номера строк, адреса, номера значений `$1…$5` и вывод `info locals` в статье получены из настоящего прогона, а не написаны от руки.
> 8. Ловушки. Пересечение большое (три ловушки почти дословно совпадают). → **Решение:** взяты ловушки A про `-g`, про `-O2`/`<optimized out>` и про выход за границы массива; ловушки Б про «отладчик — часть компилятора?», про step over/step into и про значение `32767` у неинициализированной переменной; общая ловушка про точку останова и точку наблюдения — в редакции Б (короче), про «ошибка пропала под отладчиком» — в редакции A (с перечнем причин).
>
> **Итог:** определение — A, с добавлением «или подключается к уже работающей» от Б. От A взяты: независимость `-g` и оптимизации (и то, что `-g` не замедляет программу), принципиальная неспособность отладчика диагностировать UB, различение отладчика и встроенных в программу `assert`/`static_assert`, методический совет про гипотезу и минимальный пример. От Б взяты: различение отладки и отладчика, подробный перечень понятий с командами GDB, условная точка останова, список распространённых отладчиков, «гейзенбаг», пример с целочисленным делением, совет начинать с `bt`. Расхождений по фактам между авторами не обнаружено; арбитр перестроил пример так, чтобы в нём был осмысленный стек вызовов, и заменил оба сеанса отладчика одним, снятым с реального прогона GDB.
