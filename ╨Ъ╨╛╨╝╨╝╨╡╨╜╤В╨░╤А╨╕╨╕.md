# Комментарии

> [!abstract] Определение
> **Комментарии** (*comments*) — фрагменты [[Текст программы|текста программы]], адресованные человеку и не влияющие на смысл программы: на третьей фазе трансляции каждый комментарий заменяется одним пробельным символом. В C++ есть две формы: строчная — от `//` до конца логической строки, и блочная — от `/*` до ближайшего `*/`.

## Примечания и тонкости

- Комментарий заменяется именно **пробелом**, а не пустотой. Поэтому `int/**/x = 1;` — корректное [[Объявление|объявление]] (`int` и `x` остаются двумя лексемами), а `a/**/b` ни при каких условиях не склеится в `ab`.
- Блочные комментарии **не вкладываются**: комментарий закрывается первым же встреченным `*/`, а всё после него — снова обычный текст программы. В `/* внешний /* внутренний */ хвост */` остаток «`хвост */`» становится кодом и даёт ошибку компиляции; GCC с `-Wall` дополнительно предупреждает `"/*" within comment` (см. [[Предупреждения компилятора]]).
- Чтобы временно отключить блок, внутри которого уже есть блочные комментарии, используют `#if 0 … #endif`. Но содержимое всё равно разбивается на препроцессорные лексемы, потому что разбиение (фаза 3) происходит раньше вычисления `#if` (фаза 4) и для всего файла целиком: непарная одинарная кавычка вроде `don't` внутри выключенного блока вызовет диагностику.
- Комментарии исчезают на фазе 3, а директивы [[Препроцессор|препроцессора]] выполняются на фазе 4. Отсюда сразу три следствия: комментарий не попадает в тело [[Макрос|макроса]] (`#define N 10 // десять` раскрывается ровно в `10`); макросом нельзя «создать» комментарий (`#define C //` даёт пустой макрос, потому что к фазе 4 `//` в самой директиве уже заменено пробелом); внутри комментария директивы препроцессора не выполняются.
- Последовательности `//` и `/*` внутри символьного или [[C-строки и строковые литералы|строкового литерала]] комментария не начинают, и наоборот — внутри одного вида комментария знаки другого ничего не значат. Причина общая: литералы и комментарии распознаются одновременно, на одной и той же фазе 3, и литерал «сильнее».
- Склейка строк по `\` (фаза 2) идёт **раньше** распознавания комментариев (фаза 3). Поэтому обратная косая в конце строчного комментария переносит комментарий на следующую строку, и следующая инструкция молча исчезает; GCC сообщает об этом предупреждением `multi-line comment` (`-Wcomment`).
- Незакрытый `/*` до конца единицы трансляции делает программу некорректной (GCC: `error: unterminated comment`). «Переползти» через `#include` незакрытый комментарий не может: каждый включаемый файл проходит фазы 1–4 самостоятельно.
- Документирующие комментарии (`///`, `/** … */`, `//!`) — соглашение внешних инструментов вроде Doxygen, из них генерируется документация. Для самого языка это обычные комментарии без какого-либо особого статуса.
- **На практике:** комментарий должен объяснять **почему** сделано так, а не пересказывать, что написано в коде: `i++; // увеличиваем i` бесполезен, а `// +1: индексы в файле начинаются с единицы` полезен. Устаревший комментарий хуже отсутствующего — он обманывает читателя; закомментированный код в репозитории не хранят, для истории есть система контроля версий.

## Пример

```cpp
#include <iostream>

int main() {
    int a = 10, b = 2;
    int* p = &b;
    int/* комментарий = один пробел */x = a;    // то же, что int x = a;
    int r = a / *p;                             // пробел обязателен: "a/*p" открыло бы комментарий
    std::cout << "// внутри литерала это не комментарий\n";
    std::cout << x << ' ' << r << '\n';         // выведет: 10 5
#if 0   // так отключают блок, внутри которого уже есть /* ... */
    std::cout << a;  /* старый комментарий */
#endif
}
```

Первой строкой программа выведет `// внутри литерала это не комментарий`, второй — `10 5`. Строка `int r = a / *p;` — единственное место, где пробел обязателен по лексическим причинам: записанное подряд `a/*p` открыло бы блочный комментарий, и остаток текста до ближайшего `*/` исчез бы из программы.

## Ловушки на экзамене

- **«Сколько закрывающих последовательностей нужно для `/* /* */ */`?»** — одна: комментарий закрывается первым `*/`. Остаток `*/` — ошибка, такой лексемы в языке нет; GCC выдаёт предупреждение `"/*" within comment` и ошибку на остатке.
- **«Что не так в строке `r = a/*p;`, где `p` — указатель?»** — символы `/*` образуют начало комментария, а не деление на разыменованный указатель: остаток текста до ближайшего `*/` исчезает. Нужен пробел или скобки: `a / *p`, `a/(*p)`.
- **«`int/**/x = 1;` — это корректная конструкция?»** — да, и именно потому, что комментарий заменяется пробелом, а не удаляется: иначе получилось бы имя `intx`.
- **«Почему после строки `// путь C:\` „пропала“ следующая строка кода?»** — обратная косая в конце строки склеивает строки на фазе 2, то есть раньше, чем распознаются комментарии (фаза 3), поэтому следующая строка тоже стала комментарием. Ошибки компиляции при этом нет, только предупреждение `multi-line comment`.
- **«Комментарии удаляет препроцессор?»** — нет: они исчезают на фазе 3, до работы препроцессора на фазе 4. Отсюда и то, что `#define C //` не превращает остаток строки в комментарий: к моменту обработки директивы `//` в ней уже заменено пробелом, и макрос оказывается пустым.
- **«Замедляют ли комментарии программу или увеличивают исполняемый файл?»** — нет: они исчезают на третьей фазе трансляции, задолго до генерации кода.

## Связанные термины

- [[Текст программы]] — то, частью чего комментарии являются до фазы 3 и перестают быть после.
- [[Препроцессор]] — работает на фазе 4, уже после удаления комментариев, поэтому комментариями управлять не может.
- [[Предупреждения компилятора]] — `-Wcomment` ловит мнимую вложенность и продление комментария обратной косой.
- [[C-строки и строковые литералы]] — место, где `//` и `/*` комментария не начинают.
- [[Алфавит языка программирования]] — внутри комментария допустим любой символ исходного файла, включая не входящие в базовый набор.
- [[Макрос]] — комментарий в строке `#define` в тело макроса не попадает, и создать комментарий макросом нельзя.

## Протокол спора

> [!quote]- Как рождалось определение
> **Версия A (Формалист):** «Комментарии (*comments*) — фрагменты текста программы, адресованные читателю и не влияющие на её смысл: на третьей фазе трансляции каждый комментарий заменяется одним пробельным символом. В C++ есть две формы: блочная — от `/*` до ближайшего `*/`, и строчная — от `//` до конца строки.»
>
> **Версия Б (Педагог-практик):** «Комментарии (*comments*) — фрагменты текста программы, предназначенные только для человека: на ранней стадии трансляции компилятор заменяет каждый комментарий одним пробелом, поэтому комментарии не влияют на поведение программы. В C++ комментарий записывается либо от `//` до конца строки, либо между `/*` и `*/`.»
>
> **Спорные пункты:**
> 1. Фактических ошибок не обнаружено ни у одной стороны: проверено отсутствие вложенности блочных комментариев, предупреждение `"/*" within comment`, раскрытие `#define N 10 // десять` в `10`, диагностика непарного апострофа внутри `#if 0` и пустота макроса `#define C //`.
> 2. Номер фазы внутри определения. A: фаза 3 должна быть названа в самом определении — именно она отличает комментарий от «текста, который компилятор игнорирует», и из неё выводятся все остальные тонкости. Б: «на ранней стадии трансляции», номер фазы только в примечаниях. → **Решение:** прав A, «ранняя стадия» ничего не определяет. В определение взята формулировка A.
> 3. «До конца строки» или «до конца логической строки». Б: до конца **логической** строки. A: признал формулировку Б точнее своей. → **Решение:** взято у Б: слово «логической» уже содержит в себе всю историю со склейкой по `\`.
> 4. Полнота следствий из порядка фаз 3 и 4. A: Б даёт только одно направление (комментарий не попадает в тело макроса), а нужны оба — и то, что макросом нельзя создать комментарий, и то, что внутри комментария директивы не выполняются. → **Решение:** взято у A, все три следствия собраны в один пункт; поведение `#define C //` проверено компилятором.
> 5. Незакрытый `/*`. A: программа некорректна, и через `#include` незакрытый комментарий не распространяется, потому что каждый включаемый файл проходит фазы 1–4 сам. Б: пункта нет. → **Решение:** взято у A; сообщение GCC `error: unterminated comment` проверено.
> 6. Почему литерал «сильнее» комментария. A: потому что литералы и комментарии распознаются одновременно на фазе 3. Б: подано как отдельное эмпирическое правило. → **Решение:** взята причина от A, а компактная формулировка Б «внутри одного вида комментария знаки другого ничего не значат» сохранена в том же пункте.
> 7. Повторы. A: у Б пункт «что писать в комментариях» и пункт «На практике» говорят об одном (культура комментирования), а первый пункт примечаний дословно пересказывает вторую фразу определения; пометки `// TODO:` к термину не относятся. → **Решение:** согласен, всё сведено в один пункт «На практике» с сохранением удачных примеров Б (`i++; // увеличиваем i`).
>
> **Итог:** определение — от A, с поправкой Б про логическую строку. Пример взят у Б целиком (это единственное место в обеих версиях, где показана необходимость пробела в `a / *p`, и блок `#if 0` с блочным комментарием внутри), в него добавлена строка `int/**/x` из примера A. От Б взяты ловушки про `a/*p` и про «замедляют ли комментарии программу». От A взяты: номер фазы в определении, незакрытый `/*` и его неспособность пройти через `#include`, полный набор следствий из порядка фаз 3 и 4, объяснение того, почему литерал сильнее комментария. Арбитр добавил причину диагностики внутри `#if 0` (разбиение на лексемы на фазе 3 раньше вычисления `#if` на фазе 4) и свёл два пункта Б о культуре комментирования в один.
