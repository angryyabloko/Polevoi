# Приоритеты операторов

> [!abstract] Определение
> **Приоритеты операторов** (*operator precedence*) — закреплённое грамматикой языка старшинство [[Оператор|операторов]], которое определяет группировку операндов в [[Выражение|выражении]] с несколькими операторами: операнд, стоящий между двумя операторами, связывается с тем из них, чей приоритет выше. При равных приоритетах группировку задаёт ассоциативность (*associativity*) — направление, в котором операторы присоединяют операнды: слева направо или справа налево.

## Примечания и тонкости

- **Приоритет ≠ порядок вычисления.** Приоритет отвечает на вопрос «что с чем считается», то есть задаёт структуру выражения во время компиляции; на вопрос «что считается раньше» он не отвечает вообще. В `f() + g() * h()` операнды группируются как `f() + (g() * h())`, но три функции могут быть вызваны в любом порядке ([[Порядок вычисления выражений]]). Смешение этих понятий — самая частая ошибка в рассуждениях о выражениях.
- **Стандарт не содержит таблицы приоритетов.** Приоритеты — следствие устройства грамматики выражений (раздел `[expr]`): каждому уровню соответствует свой нетерминал (*multiplicative-expression*, *additive-expression*, *shift-expression* и т. д.), и более «низкий» нетерминал строится из более «высоких». Привычная таблица — сводка этой грамматики; для C++20 её обычно записывают в 17 уровней (как на cppreference):

```text
 1  ::                                                    слева направо
 2  a++ a--  T(a) T{a}  a()  a[]  a.b  a->b               слева направо
 3  ++a --a  +a -a  !a ~a  (T)a  *a  &a  sizeof           справа налево
    co_await  new  delete
 4  .*  ->*                                               слева направо
 5  *  /  %                                               слева направо
 6  +  -  (бинарные)                                      слева направо
 7  <<  >>                                                слева направо
 8  <=>  (C++20)                                          слева направо
 9  <  <=  >  >=                                          слева направо
10  ==  !=                                                слева направо
11  &   (бинарный)                                        слева направо
12  ^                                                     слева направо
13  |                                                     слева направо
14  &&                                                    слева направо
15  ||                                                    слева направо
16  a?b:c  throw  co_yield  =  +=  -=  *=  /=  %=         справа налево
    <<=  >>=  &=  ^=  |=
17  ,                                                     слева направо
```

- **Справа налево** группируются только уровни 3 (префиксные [[Унарные операторы — префиксная и постфиксная формы|унарные операторы]]) и 16 ([[Оператор присваивания|присваивания]], `?:`, `throw`): `a = b = c` ≡ `a = (b = c)`, `**pp` ≡ `*(*pp)`, `-!x` ≡ `-(!x)`. Все бинарные операторы уровней 4–15 и 17 — слева направо: `a - b - c` ≡ `(a - b) - c`.
- **Постфиксные старше префиксных:** `*p++` ≡ `*(p++)` (сдвигается указатель, разыменовывается его прежнее значение), `++*p` ≡ `++(*p)` (увеличивается значение), `&a[i]` ≡ `&(a[i])`, `-x++` ≡ `-(x++)`.
- **Тернарный оператор — особый случай, не описываемый одной строкой таблицы.** Средний операнд `a ? b : c` разбирается так, будто заключён в скобки, а правый операнд может быть выражением присваивания: `c ? x : y = 1` ≡ `c ? x : (y = 1)` (в C это разбиралось бы как `(c ? x : y) = 1`).
- **Исторические «неудобные» уровни, унаследованные от C.** [[Битовые операторы|Битовые]] `&`, `^`, `|` младше [[Операторы сравнения|сравнений]]: `x & 1 == 0` ≡ `x & (1 == 0)`, то есть `x & 0` — всегда 0. Сдвиги младше сложения: `1 << n + 1` ≡ `1 << (n + 1)`. `&&` старше `||`: `a || b && c` ≡ `a || (b && c)` ([[Логические операторы]]).
- **`<<` старше сравнений**, поэтому при выводе сравнения скобки обязательны: `std::cout << a == b` — это `(std::cout << a) == b`, что не компилируется ([[Операторы ввода и вывода]]).
- **Лексический уровень предшествует синтаксическому.** `a+++b` разбирается как `a++ + b` не из-за приоритетов, а потому, что при разбиении [[Текст программы|текста программы]] на лексемы выбирается самая длинная возможная лексема (*maximal munch*): `+++` → `++`, `+`.
- **[[Перегрузка операторов|Перегрузка]] не меняет** приоритет, ассоциативность и число операндов: `std::cout << a + b` ≡ `std::cout << (a + b)`. Придумать новый оператор или повысить приоритет существующего нельзя.
- **На практике:** таблицу наизусть не учат — помнят несколько уровней и при малейшем сомнении ставят скобки: во время выполнения они не стоят ничего. Остальное ловят [[Предупреждения компилятора|предупреждения]]: `-Wparentheses` (входит в `-Wall`) сообщает о большинстве опасных сочетаний — `&` со сравнением, `<<` со сложением, `&&` внутри `||`, `a < b < c`.

## Пример

```cpp
#include <iostream>

int main() {
    static_assert(2 + 3 * 4 == 2 + (3 * 4));    // '*' старше '+'

    int a = 2, b = 3, c = 4;
    std::cout << a + b * c << '\n';       // a + (b * c): выведет 14
    std::cout << (a + b) * c << '\n';     // скобки меняют группировку: выведет 20
    std::cout << a - b - c << '\n';       // левая ассоциативность, (a - b) - c: выведет -5

    int arr[] = {10, 20};
    int* p = arr;
    int v = *p++;                         // *(p++): постфиксный ++ старше унарного *
    std::cout << v << ' ' << *p << '\n';  // выведет: 10 20

    int flags = 6;
    std::cout << ((flags & 1) == 0) << '\n';  // нужные скобки: выведет 1

    // flags & 1 == 0        // это flags & (1 == 0), т. е. всегда 0 (-Wparentheses)
    // 1 << a + 1            // это 1 << (a + 1): '+' старше '<<'
    // std::cout << a == b;  // ошибка: это (std::cout << a) == b
}
```

Выражение `(flags & 1) == 0` без скобок означало бы `flags & (1 == 0)` и давало бы 0 при любом `flags`: скобки здесь не украшение, а единственный способ получить проверку чётности.

## Ловушки на экзамене

- **Сколько уровней приоритета в C++?** — Стандарт этого не определяет: приоритеты выводятся из грамматики. Распространённая таблица для C++20 (cppreference) содержит 17 уровней; в других источниках число может отличаться из-за иной группировки.
- **«У `*` приоритет выше, значит, в `f() + g() * h()` сначала вызовутся `g` и `h`»** — Неверно. Приоритет определяет только, что перемножаются результаты `g()` и `h()`; порядок вызовов трёх функций не уточнён (*unspecified*).
- **Меняют ли скобки порядок вычисления?** — Нет, только группировку: в `(f() + g()) * h()` порядок вызовов по-прежнему не уточнён.
- **`if (x & 1 == 0)` — проверка на чётность?** — Нет: `==` старше `&`, выражение разбирается как `x & (1 == 0)`, то есть `x & 0`, и условие ложно при любом `x`. Нужно `(x & 1) == 0`.
- **Почему `std::cout << a == b;` не компилируется?** — `<<` старше `==`, поэтому выражение — `(std::cout << a) == b`: сравнение потока с `int`, для которого нет подходящего `operator==`.
- **Верно ли `0 < x < 10` проверяет попадание в интервал?** — Нет: левая ассоциативность даёт `(0 < x) < 10`; результат первого сравнения — `bool`, который после продвижения к `int` всегда меньше 10, и условие всегда истинно.
- **Что делает `*p++` — увеличивает значение или указатель?** — Указатель: постфиксный `++` связывается сильнее унарного `*`, выражение равно `*(p++)` и даёт значение по старому адресу.
- **Чем `!a == b` отличается от `!(a == b)`?** — `!` связывается сильнее `==`: первое выражение — `(!a) == b`, то есть сравнение `b` с 0 или 1.

## Связанные термины

- [[Выражение]] — то, структуру чего задают приоритеты.
- [[Порядок вычисления выражений]] — независимое понятие: когда вычисляются операнды, а не как они группируются.
- [[Оператор]] — у каждого оператора есть приоритет и ассоциативность.
- [[Унарные операторы — префиксная и постфиксная формы]] — постфиксные формы старше префиксных, отсюда разбор `*p++`.
- [[Битовые операторы]] — их приоритет ниже сравнений, что регулярно приводит к ошибкам.
- [[Логические операторы]] — `&&` старше `||`.
- [[Оператор присваивания]] — правоассоциативен, приоритет один из самых низких; ниже только «запятая».
- [[Перегрузка операторов]] — не меняет ни приоритет, ни ассоциативность, ни арность.

## Протокол спора

> [!quote]- Как рождалось определение
> **Версия A (Формалист):** «Приоритеты операторов (*operator precedence*) — правила синтаксического разбора выражения без скобок, определяющие, к какому из двух соседних операторов относится стоящий между ними операнд: он связывается с оператором более высокого приоритета, а при равных приоритетах — согласно ассоциативности (*associativity*) этого уровня (слева направо или справа налево). Приоритеты и ассоциативность задают только группировку операндов, но не порядок их вычисления.»
>
> **Версия Б (Педагог-практик):** «Приоритеты операторов (*operator precedence*) — закреплённое грамматикой языка старшинство операторов, которое определяет, какие операнды достаются каждому оператору в выражении с несколькими операторами: оператор с более высоким приоритетом связывается с операндами теснее. При одинаковом приоритете группировку задаёт ассоциативность — направление, в котором операторы присоединяют операнды: слева направо или справа налево.»
>
> **Спорные пункты:**
> 1. Род понятия: «правила синтаксического разбора» (A) против «старшинство операторов, закреплённое грамматикой» (Б). → **Решение:** род Б. Слово «старшинство» сразу объясняет, что такое приоритет, и при этом Б не теряет главного — что это свойство грамматики, а не соглашение. Формулировка A описывает не само понятие, а процедуру его применения, и для устного ответа тяжеловесна. Но точная часть A — «операнд, стоящий между двумя операторами, связывается с тем, чей приоритет выше» — оставлена: она однозначнее, чем «связывается с операндами теснее» у Б.
> 2. Оговорка «приоритеты не задают порядок вычисления» внутри определения (A). → **Решение:** вынесена в первое примечание. Регламент запрещает оговорки в определении, а Б верно делает из этого отдельный пункт. Содержательно A прав, и пункт поставлен первым как главный источник ошибок.
> 3. Форма изложения таблицы: таблица 17 уровней в блоке `text` (A) против линейной цепочки уровней (Б). → **Решение:** таблица A. Она точнее (различает `<=>` и остальные сравнения — уровни 8 и 9 в C++20, отдельно показывает `.*` и `->*`, `co_await`, `throw`, `co_yield`) и пригодна для повторения перед экзаменом; цепочка Б дублирует её, но теряет часть операторов.
> 4. Состав «неудобных» уровней. У A есть три случая (битовые ниже сравнений, сдвиги ниже сложения, `&&` выше `||`), у Б — два из трёх плюс отдельный пункт про `<<` и сравнения. → **Решение:** объединено; все три случая A плюс пункт Б про `std::cout << a == b`, подтверждённый компиляцией (`error: no match for 'operator==' (operand types are 'std::basic_ostream<char>' and 'int')`).
> 5. Разбор `c ? x : y = 1` (только у A). → **Решение:** принято и проверено компиляцией: при `c == false` присваивание выполняется, `y` получает 7, то есть разбор — `c ? x : (y = 7)`. Это показывает, что тернарный оператор не укладывается в одну строку таблицы.
> 6. Предупреждения в примере. Б намеренно оставляет в примере строку `x & 1 == 0`, вызывающую `-Wparentheses`, и поясняет это в тексте. → **Решение:** строка перенесена в комментарий. Регламент допускает предупреждения только в примере, посвящённом именно им; здесь пример о приоритетах, а сам факт предупреждения описан в примечании «На практике».
>
> **Итог:** определение — Б, с уточнением привязки операнда от A. От A взяты: таблица 17 уровней, перечень уровней с правой ассоциативностью, правило «постфиксные старше префиксных», особый случай тернарного оператора, все три исторических «неудобных» уровня, *maximal munch* для `a+++b`, перечень сочетаний, которые ловит `-Wparentheses`, ловушки про число уровней, `*p++` и `!a == b`. От Б взяты: формулировка определения, первое примечание «приоритет ≠ порядок вычисления» как отдельный пункт, пункт про `<<` и сравнения, невозможность придумать новый оператор, практический совет «таблицу не учат, ставят скобки», ловушки про скобки и порядок вычисления и про `a < b < c`. Арбитр перенёс предупреждающую строку из кода в комментарий и добавил `static_assert` как проверку группировки во время компиляции. Фактических ошибок ни у одной стороны не найдено.
