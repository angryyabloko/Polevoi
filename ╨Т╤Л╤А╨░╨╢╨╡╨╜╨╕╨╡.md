# Выражение

> [!abstract] Определение
> **Выражение** (*expression*) — последовательность [[Оператор|операторов]] и операндов, задающая вычисление; вычисление выражения может давать значение и может вызывать побочные эффекты (*side effect*). Каждое выражение имеет [[Тип данных|тип]], известный на этапе компиляции.

## Примечания и тонкости

- Первые два утверждения воспроизводят стандарт C++20 (`[expr.pre]`): «An expression is a sequence of operators and operands that specifies a computation. An expression can result in a value and can cause side effects.»
- **Из чего строится.** Операнды — это литералы (`42`), имена [[Переменная|переменных]] (`x`), вызовы [[Функция|функций]] (`square(x)`), `this` и вложенные выражения в скобках; операторы связывают их. Определение не требует наличия оператора: одиночный литерал или одно имя — уже полноценное выражение (такие выражения называют первичными, *primary expressions*; [[Лямбда-выражение|лямбда-выражение]] — тоже первичное).
- **Выражение и инструкция — разные вещи.** Выражение что-то *вычисляет*; [[Инструкции управления|инструкция]] (*statement*) что-то *делает* и задаёт ход выполнения программы. Точка с запятой превращает выражение в инструкцию-выражение (*expression statement*): `x = 5` — выражение, `x = 5;` — инструкция. `if`, `for`, `while`, `return`, а также объявления выражениями **не являются**, поэтому `int w = if (x) 1;` не компилируется.
- **Побочный эффект** — любое изменение состояния помимо вычисления значения: запись в объект (`x++`, `y = 10`), ввод-вывод (`std::cout << …`). У выражения `x + 1` побочных эффектов нет, у `x++` — есть. Формально стандарт относит к побочным эффектам изменение объекта, чтение через volatile-glvalue, вызов библиотечной функции ввода-вывода и вызов функции, делающей что-либо из перечисленного.
- **Значения может не быть:** выражение типа [[Тип void|void]] — вызов `void`-функции или `throw`-выражение — задаёт вычисление только ради побочных эффектов.
- **Категория значения.** Кроме типа, каждое выражение относится к одной из категорий значения: [[lvalue и rvalue|lvalue]] обозначает объект, имеющий место в памяти (`x`, `arr[i]`), prvalue — «просто значение» (`42`, `x + 1`). Отсюда `x + 1 = 5;` — ошибка: слева от `=` требуется lvalue. Тип выражения при этом никогда не бывает ссылочным: «ссылочность» переменной проявляется именно в категории значения выражения.
- **Присваивание в C++ — выражение**, результат которого — lvalue левого операнда. Поэтому корректны цепочки `a = b = c`, а `if (x = 0)` компилируется — частая ошибка вместо `==` ([[Оператор присваивания]]).
- Выражение и сущность — разные вещи: переменная `x` — сущность, введённая [[Объявление|объявлением]]; выражение `x` — lvalue, обозначающее [[Объект|объект]] этой переменной. Объявление `int x = 1;` выражением не является, и оператора присваивания в нём нет.
- **Не всякое выражение вычисляется.** Операнды `sizeof`, `decltype`, `noexcept` и `typeid` (для неполиморфного типа) — невычисляемые (*unevaluated operands*): компилятору нужен только их тип, поэтому `sizeof(x++)` не увеличивает `x`.
- **Группировка и порядок вычисления — разные вещи.** [[Приоритеты операторов|Приоритет]] и ассоциативность определяют лишь, какие операнды принадлежат какому оператору (`a + b * c` — это `a + (b * c)`), но не [[Порядок вычисления выражений|порядок вычисления]] подвыражений: для большинства операторов он не уточнён (*unspecified*), а два неупорядоченных побочных эффекта на один скалярный объект — UB.
- Полное выражение (*full-expression*) — выражение, не являющееся подвыражением другого; временные объекты, созданные при его вычислении, уничтожаются по его завершении. Константное выражение — выражение, вычислимое на этапе компиляции; оно требуется, например, для границы [[Встроенный массив|массива]] и в [[constexpr]]-контекстах.
- **На практике:** полезно правило «одно выражение — одно изменение»: выражения, где одна переменная меняется несколько раз (`i++ + i++`), трудно читать, а часто это ещё и UB. Обратная ошибка — инструкция-выражение без побочного эффекта (`x == 1;` вместо `x = 1;`): она бесполезна, и `-Wall` о ней предупреждает ([[Предупреждения компилятора]]).

## Пример

```cpp
#include <iostream>

int square(int v) { return v * v; }

int main() {
    int x = 3;                   // объявление: "= 3" — инициализатор, не присваивание
    int y = x + 2 * square(x);   // выражение; ';' превращает его в инструкцию
    std::cout << y << '\n';      // выведет: 21
    x++;                         // выражение с побочным эффектом
    int z = (y = 10) + 1;        // присваивание — выражение, его результат — lvalue y
    std::cout << x << ' ' << y << ' ' << z << '\n';   // выведет: 4 10 11
    std::cout << sizeof(x++) << '\n';   // операнд sizeof не вычисляется; выведет (обычно): 4
    std::cout << x << '\n';             // выведет: 4 — x не изменился
    // int w = if (x) 1;         // ошибка: if — инструкция, а не выражение
    // x + 1 = 5;                // ошибка: слева от '=' нужен lvalue
}
```

## Ловушки на экзамене

- **Являются ли `42` и `x` выражениями?** — Да, это первичные выражения: литерал и имя. Определение не требует наличия оператора; тип `42` — `int`, тип `x` — тип переменной.
- **`int x = 5;` — выражение?** — Нет, это объявление; `=` в нём часть инициализатора. Выражением является, например, `x = 5`, а с точкой с запятой — инструкция-выражение.
- **Всегда ли выражение имеет значение?** — Нет: вызов функции, возвращающей `void`, — выражение типа `void` без значения; его вычисляют только ради побочного эффекта.
- **Каков результат выражения `a = 5`?** — lvalue `a` со значением 5, а не «значение 5». Поэтому возможны цепочки `a = b = 5`, а `if (x = 0)` компилируется: `x` получает 0, и результат 0 преобразуется в `false`, поэтому тело никогда не выполняется (с `-Wall` компилятор об этом предупреждает).
- **Увеличит ли `sizeof(x++)` переменную `x`?** — Нет: операнд `sizeof` не вычисляется, компилятору нужен только его тип.
- **Задаёт ли приоритет операторов порядок вычисления?** — Нет, только группировку. В `f() + g() * h()` приоритет гарантирует лишь, что умножаются результаты `g()` и `h()`, но какая из трёх функций будет вызвана первой — не уточнено.

## Протокол спора

> [!quote]- Как рождалось определение
> **Версия A (Формалист):** «Выражение (*expression*) — последовательность операторов и операндов, задающая вычисление; вычисление выражения может давать значение и может вызывать побочные эффекты. Каждое выражение имеет тип и категорию значения, известные на этапе компиляции.»
>
> **Версия Б (Педагог-практик):** «Выражение (*expression*) — последовательность операторов и операндов, задающая вычисление; каждое выражение имеет тип, а его вычисление может давать значение и может производить побочный эффект (*side effect*) — изменение состояния программы или внешнего мира.»
>
> **Спорные пункты:**
> 1. Категория значения в определении (A) или только в примечаниях (Б). → **Решение:** в определении оставлен только тип. Б прав: в блоке 1 понятие «категория значения» ещё не введено, и устный ответ по определению A немедленно влечёт вопрос, на который студент ответить не сможет. Категория значения дана отдельным примечанием.
> 2. Расшифровка побочного эффекта внутри определения (Б: «изменение состояния программы или внешнего мира»). → **Решение:** расшифровка убрана из определения как оговорка; в примечании дана пара примеров (`x++`, вывод в поток) и формальный перечень из стандарта.
> 3. «Вырожденный случай — первичные выражения» (A). → **Решение:** формулировка изменена: важно не то, что литерал «вырожден», а то, что оператора в выражении может не быть вовсе. Сам пункт и ловушка A («определение не требует наличия оператора») сохранены.
> 4. Явное разграничение «`if`, `for`, `return` — не выражения». У A оно только подразумевается. → **Решение:** принято требование Б: разграничение *operator*/*statement* регламент выделяет как обязательное, поэтому оно сформулировано прямо, вместе с контрпримером `int w = if (x) 1;`.
> 5. Результат присваивания: «сам изменённый объект» (Б) против «lvalue левого операнда» (A). → **Решение:** формулировка A, она точнее; Б с этим согласился.
> 6. Наполнение примера. У A три `static_assert` с `decltype((…))`, которые нельзя прочитать без сноски и которые относятся к статье «lvalue и rvalue»; у Б нет ни одного невычисляемого контекста, кроме `sizeof`. → **Решение:** за основу взят пример Б (побочный эффект `x++`, присваивание как выражение, `sizeof(x++)` с последующей проверкой `x`), из версии A добавлены закомментированные строки-ошибки. Полная таксономия lvalue/xvalue/prvalue и `throw` как выражение из статьи убраны.
>
> **Итог:** определение — A без категории значения, с пометкой *side effect* из версии Б. От A взяты: цитата `[expr.pre]`, первичные выражения и `this`, перечень побочных эффектов по стандарту, невычисляемые операнды, результат присваивания как lvalue, полное выражение, «выражение и сущность — разные вещи», связка с `-Wall` на бесполезной инструкции, ловушки про приоритет и про `a = 5`. От Б: «из чего строится выражение» на языке студента, прямое разграничение с `if`/`for`/`return`, побочный эффект на примерах, следствие `x + 1 = 5` из категорий значения, правило «одно выражение — одно изменение», ловушки про `void`-выражение, `if (x = 0)` и `sizeof(x++)`. Арбитр объединил дублирующие ловушки A про `5`/`x` и `int x = 5;`, свёл `if (x = 0)` и результат присваивания в одну ловушку и убрал `throw` как выражение: в блоке 1 исключения ещё не введены.
