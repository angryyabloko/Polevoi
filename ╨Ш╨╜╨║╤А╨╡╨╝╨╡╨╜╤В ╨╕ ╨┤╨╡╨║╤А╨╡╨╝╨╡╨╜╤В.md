# Инкремент и декремент

> [!abstract] Определение
> **Инкремент** (*increment*, `++`) и **декремент** (*decrement*, `--`) — [[Унарные операторы — префиксная и постфиксная формы|унарные операторы]], которые как побочный эффект увеличивают или уменьшают значение своего операнда на единицу: для арифметического операнда — на 1, для указателя — на один элемент. Операнд должен быть модифицируемым [[lvalue и rvalue|lvalue]]. Префиксная форма (`++x`) даёт в качестве результата сам изменённый операнд, постфиксная (`x++`) — его значение, существовавшее до изменения.

## Примечания и тонкости

- **Как запомнить.** Префиксная форма — «сначала увеличь, потом отдай»; постфиксная — «запомни старое, увеличь, отдай запомненное». Если результат выражения не используется (`i++;` отдельной инструкцией или в третьей части заголовка `for`), обе формы делают в точности одно и то же.
- **Эквиваленты.** Для встроенных типов `++x` — то же, что `x += 1`, а `--x` — `x -= 1` ([[Оператор присваивания|составное присваивание]]). Для `x++` побочный эффект тот же, но значением выражения является копия старого значения, поэтому постфиксная форма обязана её где-то хранить.
- **«Потом» не значит «после инструкции».** Постфиксный `++` не откладывает изменение до конца строки: гарантируется лишь, что **значением выражения** будет старое значение; вычисление этого значения секвенировано перед модификацией операнда, но сама модификация происходит при вычислении выражения, а не после инструкции.
- **Что можно увеличивать.** Операнд — модифицируемое lvalue арифметического типа (кроме `bool`) или указатель на полный тип объекта: [[Переменная|переменная]], элемент массива, поле объекта, `*p`. Нельзя: литерал (`5++`), значение выражения (`(a + b)++`), [[Константность|константу]], массив, функцию, указатель на неполный тип — в частности, `void*` инкрементировать нельзя.
- **Изменения в стандарте.** `++` для операнда типа [[Логический тип|bool]] (превращение в `true`) было объявлено устаревшим и **удалено в C++17**: начиная с C++17 такая программа ill-formed; `--` для `bool` не допускался никогда. В C++20 применение `++`/`--` к операнду с квалификатором `volatile` объявлено устаревшим.
- **Указатели и итераторы.** `++p` сдвигает указатель на следующий элемент: адрес растёт на `sizeof(T)` байт, а не на единицу ([[Арифметика указателей]]). Получить значение «за последним элементом» законно, разыменовывать его — нет. Так же `++it` переводит [[Итератор|итератор]] к следующему элементу контейнера.
- **Разный результат — разные возможности.** `++x` даёт саму переменную (lvalue), поэтому допустимы `++x = 10` и `&++x`. `x++` даёт временную копию (prvalue), поэтому `x++ = 10` и `x++ ++` — ошибки компиляции.
- **Приоритет:** постфиксные `++`/`--` сильнее разыменования, префиксные — на одном с ним уровне и группируются справа налево: `*p++` — это `*(p++)`, `++*p` — это `++(*p)`. См. [[Приоритеты операторов]].
- **Несколько изменений в одном выражении.** Если в одном выражении объект изменяется дважды или изменяется и читается, а эти вычисления не секвенированы друг относительно друга, поведение **не определено**: `i++ + ++i`, `n = ++i + i`, `k = ++k + k++` — UB в любой версии стандарта, потому что операнды бинарных `+` между собой не секвенированы. C++17 при этом сделал определёнными те случаи, где порядок задан: в присваивании `E1 = E2` правый операнд секвенирован перед левым, поэтому `i = i++ + 2` даёт `i == 2`, а `a[i] = i++` записывает в `a[1]`; левый операнд `<<` секвенирован перед правым, поэтому `std::cout << i++ << i` при `i == 0` выводит `01`. Подробнее — [[Порядок вычисления выражений]].
- **Диагностика отстала от стандарта.** g++ 13 выдаёт предупреждение `-Wsequence-point` на `i = i++ + 2` и на `std::cout << i++ << i` даже с `-std=c++20`, хотя эти выражения определены. Это веский повод так не писать, но не доказательство UB (см. [[Предупреждения компилятора]]). Безопасное правило для экзамена и практики одно: переменная, которую изменяют, больше в этом выражении не упоминается.
- **Что быстрее — `++i` или `i++`?** Для встроенных типов разницы нет: компилятор порождает одинаковый код. Для классов (итераторы, «тяжёлые» объекты) постфиксная форма обязана сделать копию старого состояния, поэтому идиоматично писать `++it`. Для своих типов формы [[Перегрузка операторов|перегружаются]] отдельно: `T& operator++()` и `T operator++(int)`. Перегруженные формы, записанные в операторной форме, наследуют правила секвенирования встроенных.
- **На практике:** счётчики [[Инструкции циклов|циклов]] (`for (int i = 0; i < n; ++i)`), проход по массиву указателем или по контейнеру итератором, идиома `while (n--)` — «повторить `n` раз». Смешивать изменение переменной и её чтение в одном выражении не следует независимо от формальной определённости: читаемость страдает раньше, чем корректность.

## Пример

```cpp
#include <iostream>
#include <vector>

int main() {
    int i = 5;
    int a = ++i;                           // сначала увеличить, потом взять: i == 6, a == 6
    int b = i++;                           // взять старое (6), увеличить: i == 7, b == 6
    std::cout << a << ' ' << b << ' ' << i << '\n';   // выведет: 6 6 7

    int n = 3;
    while (n--) std::cout << n << ' ';     // проверяется старое значение: 3, 2, 1, 0
    std::cout << "| n = " << n << '\n';    // выведет: 2 1 0 | n = -1

    std::vector<int> v{10, 20, 30};
    auto it = v.begin();
    ++it;                                  // шаг — один элемент, а не один байт
    std::cout << *it++ << '\n';            // выведет: 20, после чего it указывает на 30
    std::cout << *it << '\n';              // выведет: 30

    double d = 1.5;
    ++d;                                   // для вещественных типов ++ разрешён
    std::cout << d << '\n';                // выведет: 2.5

    // bool f = false; ++f;                // ошибка начиная с C++17: ++ для bool удалён
    // int k = 0; k = ++k + k++;           // UB: два несеквенированных изменения k
    // 5++;                                // ошибка: операнд должен быть модифицируемым lvalue
}
```

Цикл `while (n--)` выполняется ровно 3 раза, но в теле `n` уже уменьшено, а после цикла равно `-1`: последняя, ложная проверка тоже уменьшила `n`. Выражение `*it++` разбирается как `*(it++)`: постфиксный `++` старше унарного `*`, поэтому разыменовывается старое значение итератора, а сам итератор уже сдвинут.

## Ловушки на экзамене

- **«Чем `++i` отличается от `i++`?»** — обе формы увеличивают `i` на 1; различается только значение выражения: у префиксной — новое значение (и это сама переменная), у постфиксной — копия старого. Разница видна лишь тогда, когда результат используется.
- **«Что выведет `int i = 5; std::cout << i++ + ++i;`?»** — ни `12`, ни `13`: это UB, `i` изменяется дважды, и операнды `+` между собой не секвенированы. Правильный ответ — «так писать нельзя, результат не определён».
- **«`i = i++ + 2` — неопределённое поведение?»** — до C++17 да, с C++17 нет: правый операнд присваивания секвенирован перед левым, и `i` становится равным 2. Но `i = ++i + i++` — UB в любой версии. То же различие: `a[i] = i++` с C++17 определено, а `i++ + ++i` нет.
- **«Правда ли, что в `x++` увеличение происходит после выполнения всей инструкции?»** — нет. Гарантировано только, что значением выражения `x++` будет старое значение; переменная меняется при вычислении этого выражения, и строить логику на «моменте» изменения внутри той же инструкции нельзя.
- **«Чему равно `n` после `int n = 3; while (n--) {}`?»** — `-1`: условие проверяет старое значение (3, 2, 1, 0), а уменьшение происходит и при последней, ложной проверке.
- **«Можно ли написать `5++` или `(a + b)++`?»** — нет: операнд должен быть модифицируемым lvalue, то есть обозначать объект в памяти, а `5` и `a + b` — просто значения.
- **«`++b` для `bool b`?»** — ошибка компиляции начиная с C++17; до C++17 это была устаревшая возможность, превращавшая операнд в `true`.
- **«На сколько изменится `int* p` после `++p`?»** — на `sizeof(int)` байт, то есть на один элемент. Значение выражения `p++` — старый адрес.
- **«Чем плох `it++` для итератора?»** — постфиксная форма обязана создать и вернуть копию итератора до сдвига; если копия не используется, это лишняя работа. Для `int` разницы нет.

## Связанные термины

- [[Унарные операторы — префиксная и постфиксная формы]] — общее понятие о формах записи, к которому относятся `++` и `--`.
- [[Оператор присваивания]] — `++x` эквивалентно `x += 1`.
- [[Порядок вычисления выражений]] — объясняет, какие комбинации `++` в одном выражении определены, а какие UB.
- [[lvalue и rvalue]] — что может быть операндом и что дают две формы.
- [[Арифметика указателей]] — смысл «шага на один элемент» для указателей.
- [[Итератор]] — главный потребитель `++` в реальном коде.
- [[Инструкции циклов]] — типичное место применения инкремента.
- [[Логический тип]] — единственный арифметический тип, для которого `++` запрещён.

## Протокол спора

> [!quote]- Как рождалось определение
> **Версия A (Формалист):** «Инкремент (*increment*, `++`) и декремент (*decrement*, `--`) — унарные операторы, которые как побочный эффект увеличивают или уменьшают значение своего операнда на единицу: для арифметического операнда — на 1, для указателя — на один элемент. Операнд должен быть модифицируемым lvalue арифметического типа (кроме `bool`) либо указателем на полный тип объекта. Префиксная форма даёт в качестве результата сам изменённый операнд (lvalue), постфиксная — его значение до изменения (prvalue).»
>
> **Версия Б (Педагог-практик):** «Инкремент `++` и декремент `--` (*increment, decrement*) — унарные операторы, которые изменяют свой операнд — изменяемое lvalue, — увеличивая или уменьшая его значение на единицу. Префиксная форма (`++x`) возвращает сам операнд уже с новым значением, постфиксная (`x++`) — копию его старого значения, существовавшего до изменения.»
>
> **Спорные пункты:**
> 1. Главное разногласие партии — что именно изменил C++17. A: `i = i++ + 2` с C++17 **определено** и даёт `i == 2`; `std::cout << i++ << i` определено и выводит `01`; `a[i] = i++` тоже определено; «во многих учебниках они по инерции названы UB». Б: «C++17 узаконил часть случаев», но в ловушках и примечаниях настойчиво сводит тему к «несколько изменений в одном выражении — UB» и не разделяет определённые и неопределённые случаи. → **Решение:** прав A, и это проверено компилятором. Запуск `int i = 0; std::cout << i++ << i;` даёт `01`; `int j = 0; j = j++ + 2;` даёт `j == 2`; вычисление `i = i++ + 2` и `a[i] = i++` внутри `constexpr`-функции проходит константное вычисление и подтверждает записанные значения. Основание в стандарте: [expr.ass] — правый операнд простого присваивания секвенирован перед левым (C++17), и для `<<` левый операнд секвенирован перед правым, причём с C++17 это правило распространяется и на перегруженный оператор в операторной форме. В итог вошла формулировка A, но с явным перечнем того, что UB **осталось**, — за это отвечала позиция Б.
> 2. Какой пример выбрать для ловушки про UB. A использует `i = ++i + i++`, Б — `i++ + ++i`. → **Решение:** взяты оба: они показывают, что дело не в постфиксной форме, а в двух несеквенированных изменениях операндов бинарного `+`. Утверждение Б, что `i++ + ++i` — UB, верно и в C++20.
> 3. Формулировка Б «C++17 узаконил часть случаев, но g++ по-прежнему предупреждает о них». → **Решение:** принята как дополнение к решению по пункту 1 — и проверена: g++ 13.3 с `-std=c++20 -Wall` действительно выдаёт `-Wsequence-point` и на `i = i++ + 2`, и на `std::cout << i++ << i`. Оба автора об этом пишут, и оба делают верный вывод: предупреждение — не доказательство UB, но достаточный повод так не писать.
> 4. Ограничения на операнд. A перечисляет их в определении (арифметический тип кроме `bool`, указатель на полный тип), Б — в примечаниях, но называет больше практических случаев (`5++`, `(a + b)++`, константа). → **Решение:** определение оставлено коротким («модифицируемое lvalue») по версии Б, полный перечень ограничений от A и практические случаи от Б сведены в одно примечание. Регламент прямо требует убирать оговорки из определения.
> 5. Категории значения в определении. A называет lvalue и prvalue прямо в определении, Б — только в примечании. → **Решение:** из определения термины убраны (они мало говорят первокурснику в первом блоке), а примечание «разный результат — разные возможности» от Б сохранено с примерами `&++x` и `x++ ++`.
> 6. Что делать с `while (n--)` и «название C++ — шутка на эту тему». → **Решение:** идиома `while (n--)` от Б принята: она даёт и пример, и ловушку про значение `n` после цикла. Реплика про название языка из итога убрана как не относящаяся к делу.
> 7. Изменения стандарта помимо секвенирования. Удаление `++` для `bool` в C++17 есть у обоих; устаревание `++` для `volatile` в C++20, запрет для `void*` и законность адреса «за последним элементом» — только у A. → **Решение:** приняты все три пункта A.
>
> **Итог:** определение — гибрид: род и «побочный эффект ... на единицу, для указателя — на один элемент» от A, короткое «модифицируемое lvalue» и описание результата обеих форм от Б. От A взяты: полный перечень ограничений на операнд, `volatile` в C++20, разбор секвенирования с C++17 и его граница, наследование правил секвенирования перегруженными операторами, ловушки про `f(++i, ++i)`-класс выражений (сведённые к различию «определено / UB»), `*it++` в примере. От Б: мнемоника двух форм, пункт «"потом" не значит "после инструкции"», перечень того, что нельзя инкрементировать, `++x = 10` и `&++x`, вопрос «что быстрее», идиома `while (n--)` с ловушкой про `n == -1`, безопасное правило «изменяемая переменная больше в выражении не упоминается». Арбитр исправил главное: размытое «C++17 узаконил часть случаев» у Б заменено точным списком определённых и неопределённых выражений, подтверждённым компилятором и стандартом; итоговый пример проверен и выводит `6 6 7`, `2 1 0 | n = -1`, `20`, `30`, `2.5`.
